# Ошибки, которые нужно исправить перед production

Документ содержит только актуальные дефекты ветки `railway`. Пункты расположены
в порядке исправления.

## Возможности по ролям: что должно быть и что работает сейчас

Ниже перечислены ожидаемые сценарии ролей по backend API и предметной области
проекта. Наличие кнопки или экрана не считается готовой функцией, если результат
не сохраняется в PostgreSQL.

### Сотрудник

#### Что сотрудник должен уметь

- видеть профиль, назначенный стек, грейд и программу обучения;
- просматривать состав программы и учебные материалы;
- отмечать материалы изученными;
- видеть свою матрицу компетенций и прогресс;
- видеть список назначенных заданий и их статусы;
- начинать задание;
- отправлять текст, ссылки и файлы на проверку;
- видеть количество попыток и историю сдач;
- читать решение и комментарий эксперта;
- исправлять и повторно отправлять возвращённую работу.

#### Что работает сейчас

- вход и восстановление профиля через `/auth/me`;
- отображение профиля;
- экраны программы, матрицы, списка и карточки заданий;
- локальные формы старта и сдачи;
- загрузка файла в S3 вызывается через API.

#### Чего не хватает или что работает неправильно

- программа, матрица и задания отображаются из mock-констант, а не из БД;
- старт задания не отправляется в backend;
- submission не создаётся в PostgreSQL;
- история попыток и прогресс существуют только в React state;
- после обновления страницы изменения пропадают;
- материал нельзя полноценно открыть и отметить изученным через UI;
- файл загружается до создания реальной сдачи и может остаться осиротевшим;
- frontend использует статусы, отличающиеся от backend;
- нет корректного refresh token flow;
- нет понятных loading, empty и error состояний для основных экранов.

**Итог:** интерфейс сотрудника визуально наиболее полный, но основной учебный
сценарий пока является демонстрацией и не работает сквозным образом с БД.

### Эксперт

#### Что эксперт должен уметь

- видеть очередь работ, ожидающих проверки;
- открывать сдачу, текст, ссылки и прикреплённые файлы;
- принимать работу или возвращать её с обязательным комментарием;
- видеть историю попыток сотрудника;
- просматривать сотрудников и их прогресс;
- назначать сотрудникам программы обучения;
- создавать и редактировать программы и их состав;
- создавать задания и материалы;
- создавать и редактировать блоки матрицы и компетенции;
- отслеживать прогресс по компетенциям.

#### Что работает сейчас

- вход и отображение профиля;
- вкладка «Очередь ревью»;
- таблица файлов сдач загружается из backend;
- можно запросить presigned URL и открыть файл;
- backend уже содержит endpoints очереди, карточки сдачи и review;
- backend содержит endpoints программ, матриц, компетенций и заданий.

#### Чего не хватает или что работает неправильно

- очередь review строится из локального массива mock-заданий, а не из
  `GET /api/v1/expert/submissions`;
- решение эксперта не отправляется в backend и пропадает после обновления;
- используются неправильные статусы `approved/pending` вместо
  `accepted/on_review`;
- нет полноценной карточки реальной сдачи и истории попыток из API;
- список файлов отделён от конкретных работ и показывает ID вместо понятных
  данных сотрудника;
- нет интерфейса управления программами;
- нет интерфейса создания заданий и материалов;
- нет интерфейса управления матрицей и компетенциями;
- нет назначения программ сотрудникам;
- нет экрана прогресса конкретного сотрудника;
- профиль эксперта почти пуст, потому что для роли нет отдельного dashboard.

**Итог:** для эксперта реализован макет очереди и частичная работа с файлами, но
основные экспертные действия и управление учебным контентом отсутствуют.

### Администратор

#### Что администратор должен уметь

- видеть сводку по пользователям, ролям, программам и активности;
- создавать пользователя;
- открывать и редактировать карточку пользователя;
- назначать роль, стек, грейд, должность и дату начала работы;
- блокировать и разблокировать пользователя;
- назначать программу обучения;
- видеть прогресс сотрудника;
- управлять экспертами и сотрудниками;
- управлять справочниками, программами, заданиями и матрицами либо иметь доступ
  к тем же инструментам, что и эксперт;
- контролировать корректность начальных данных системы.

#### Что работает сейчас

- вход и отображение профиля;
- загрузка списка пользователей из backend;
- отображение роли, стека и статуса пользователя;
- назначение или смена стека сотруднику сохраняется через API;
- backend содержит endpoints создания пользователя, редактирования профиля,
  блокировки и назначения программы.

#### Чего не хватает или что работает неправильно

- нет dashboard и сводной информации;
- нет формы создания пользователя;
- нет карточки и полноценного редактирования пользователя;
- нельзя назначить роль, грейд, должность и программу через UI;
- блокировка меняется только локально и не сохраняется в БД;
- нет просмотра прогресса сотрудника;
- нет интерфейса управления программами, заданиями и матрицами;
- профиль администратора использует общую карточку, поэтому показывает пустые
  грейд, должность и дату начала работы;
- если в БД существует только bootstrap-администратор, реестр содержит одну
  строку и почти не предлагает действий;
- нет отдельного пустого состояния с предложением создать первого сотрудника.

**Итог:** административный интерфейс сейчас является реестром пользователей с
частичным назначением стека. Для управления системой его недостаточно.

### Общий критерий готовности ролей

Для каждой роли нужно выполнить сквозную проверку:

1. Действие выполняется через реальный endpoint.
2. Backend проверяет роль и доступ к конкретной сущности.
3. Результат сохраняется в PostgreSQL/S3.
4. После обновления страницы отображается то же состояние.
5. Ошибка backend показана пользователю и не подменяется локальным успехом.

## P0 — основные сценарии не работают с базой данных

### 1. Старт задания не сохраняется

**Ошибка:** кнопка старта меняет только React state. После обновления страницы
задание снова становится не начатым.

**Где:** `frontend/src/App.jsx`, функция `handleStartTask`.

**Исправить:** вызывать:

```http
POST /api/v1/assignments/{task_id}/start
```

Обновлять интерфейс ответом API, а не локально сформированным объектом.

**Готово, когда:** после старта и обновления страницы статус остаётся
`in_progress`.

### 2. Сдача задания не создаётся в PostgreSQL

**Ошибка:** форма сдачи обновляет локальный массив `tasks`, но endpoint сдачи не
вызывается. После обновления страницы результат пропадает.

**Где:** `frontend/src/App.jsx`, функция `handleSubmitTask`.

**Исправить:** вызывать:

```http
POST /api/v1/assignments/{task_id}/submit
```

Передавать поля backend-схемы: `content`, `link`, `file_key`.

**Готово, когда:** в таблице `submissions` появляется запись, а после обновления
страницы пользователь видит отправленную работу и статус `on_review`.

### 3. Решение эксперта не сохраняется

**Ошибка:** эксперт принимает или возвращает работу только внутри React state.

**Где:** `frontend/src/App.jsx`, функция `handleReviewSubmit`.

**Исправить:** вызывать:

```http
POST /api/v1/submissions/{submission_id}/review
```

Передавать `decision: "accepted" | "returned"` и `comment`.

**Готово, когда:** решение сохраняется в PostgreSQL и остаётся после обновления
страницы.

### 4. Frontend использует неправильные API-контракты

**Ошибка:** существующие helpers отправляют запросы на неправильные URL и
используют неправильные методы и поля.

**Где:** `frontend/src/api.js`, функции `submitTaskApi` и
`reviewSubmissionApi`.

**Исправить:** привести helpers к контрактам из пунктов 2–3 и использовать их в
`App.jsx`.

**Готово, когда:** запросы не получают `404`, `405` или `422`, а типы статусов и
payload совпадают с backend.

### 5. Frontend и backend используют разные статусы

**Ошибка:** frontend использует `pending` и `approved`, backend — `on_review` и
`accepted`.

**Исправить:** хранить в состоянии значения backend:

```text
not_started
in_progress
on_review
accepted
returned
```

Русские подписи формировать только при отображении.

**Готово, когда:** frontend не преобразует серверные статусы в собственные
доменные значения.

## P0 — программы, матрицы и задания показывают mock-данные

### 6. Загруженные данные API не используются

**Ошибка:** `dbPrograms` и `dbMatrixBlocks` заполняются, но UI продолжает
рендерить `LEARNING_PROGRAMS`, `MATRICES` и `INITIAL_TASKS`.

**Где:** `frontend/src/App.jsx`.

**Исправить:** строить экраны программы, матрицы и заданий из ответов API.
Защищённые запросы выполнять только после восстановления сессии.

**Готово, когда:** изменение данных в PostgreSQL отображается во frontend без
правки `App.jsx`.

### 7. Ошибки загрузки данных скрываются

**Ошибка:** часть ошибок выводится только через `console.warn`, поэтому
пользователь видит пустой или устаревший экран.

**Исправить:** добавить для программ, матриц и заданий состояния loading, error,
empty и кнопку повторной загрузки.

**Готово, когда:** при недоступном API пользователь видит понятное сообщение, а
не mock-данные.

## P0 — нарушен сценарий загрузки файлов

### 8. Файл загружается до создания submission

**Ошибка:** frontend генерирует случайный `submission_id`. Backend сохраняет файл
даже тогда, когда такой submission не существует. Возникают осиротевшие записи и
объекты S3.

**Где:** `frontend/src/App.jsx` и `api/content.py`.

**Исправить:** определить один серверный сценарий:

1. Создать submission и получить реальный ID.
2. Загрузить файлы для этого ID.
3. Проверить владельца submission на backend.
4. Связать файл со сдачей в одной согласованной операции.
5. Очищать загруженный объект при частичной ошибке.

**Готово, когда:** в `files.entity_id` всегда находится ID существующей сдачи и
у пользователя не остаются осиротевшие файлы.

### 9. Backend доверяет произвольному `file_key`

**Ошибка:** клиент может передать чужой или несуществующий ключ объекта.

**Где:** `app/schemas/submissions.py` и `api/submissions.py`.

**Исправить:** перед привязкой проверить запись `files`, владельца, статус
`uploaded`, тип `submission` и соответствие конкретной сдаче.

**Готово, когда:** невозможно отправить чужой или выдуманный `file_key`.

## P1 — административные действия и сессия

### 10. Блокировка пользователя работает только визуально

**Ошибка:** `toggleUserActive` меняет React state, но не PostgreSQL.

**Где:** `frontend/src/App.jsx`.

**Исправить:** использовать существующий `blockUserApi`, обновлять строку только
после успешного ответа и показывать ошибку при отказе.

**Готово, когда:** заблокированный пользователь остаётся заблокированным после
обновления страницы и не может войти.

### 11. Refresh token не используется

**Ошибка:** frontend сохраняет только access token и завершает сессию при первом
`401`.

**Где:** `frontend/src/api.js`.

**Исправить:** реализовать один refresh-запрос при `401`, повтор исходного
запроса и logout при неуспешном refresh. Не допускать нескольких параллельных
refresh-запросов.

**Готово, когда:** пользователь продолжает работу после истечения access token,
если refresh token ещё действителен.

## P1 — ошибки backend и базы данных

### 12. Доступ к материалам и заданиям проверяется не везде

**Ошибка:** авторизованный пользователь может запросить некоторые материалы или
задания по известному ID, даже если они не входят в назначенную программу.

**Где:** `api/learning.py`.

**Исправить:** проверять назначенную программу при просмотре и завершении
материала, просмотре и старте задания, а также при сдаче. Для эксперта и
администратора определить отдельные права.

**Готово, когда:** сотрудник получает `403` для контента чужой программы.

### 13. `create_all()` обходит Alembic

**Ошибка:** `Base.metadata.create_all()` выполняется при импорте приложения и
может создать неполную схему без миграций.

**Где:** `main.py`.

**Исправить:** удалить `create_all()` из runtime. Структуру БД менять только
через pre-deploy команду `alembic upgrade head`.

**Готово, когда:** приложение не создаёт и не изменяет таблицы при обычном
старте.

### 14. В БД не закреплены уникальные бизнес-связи

**Ошибка:** параллельные запросы могут создать дубликаты прогресса или попыток.

**Исправить миграцией:** добавить ограничения:

- `submissions(user_id, task_id, attempt_number)`;
- `user_task_progress(user_id, task_id)`;
- `user_material_progress(user_id, material_id)`;
- `user_progress(user_id, competency_id)`;
- CHECK: в `program_items` заполнено ровно одно из `material_id` и `task_id`.

**Готово, когда:** PostgreSQL отклоняет дубликаты независимо от проверок Python.

### 15. Bootstrap администратора может конфликтовать между репликами

**Ошибка:** инициализация запускается при каждом старте приложения. Две реплики
могут одновременно попытаться создать одного пользователя.

**Исправить:** вынести bootstrap в pre-deploy/management-команду либо сделать
транзакционный upsert.

**Готово, когда:** параллельный старт реплик не создаёт дубликаты и не завершает
приложение с ошибкой.

## P1 — ошибки production serving

### 16. Нет полноценного SPA fallback

**Ошибка:** `/` и assets открываются, но прямой переход на будущий клиентский URL
может вернуть `404`.

**Где:** `main.py`, подключение `StaticFiles`.

**Исправить:** возвращать `index.html` для frontend-маршрутов, не перехватывая
`/api/*`, `/docs`, `/redoc` и `/openapi.json`.

**Готово, когда:** frontend URL открывается напрямую и после обновления страницы.

### 17. Healthcheck возвращает HTTP 200 при ошибке БД

**Ошибка:** Railway может считать сервис здоровым, когда PostgreSQL недоступна.

**Где:** `main.py`.

**Исправить:** возвращать HTTP `503` при ошибке подключения и удалить второе
неиспользуемое определение `health_check`.

**Готово, когда:** отключённая БД приводит к `503` на `/api/v1/health`.

### 18. Нет кеширования и security headers

**Исправить:** добавить:

- отсутствие длительного кеша для `index.html`;
- immutable cache для хешированных assets;
- gzip или Brotli;
- `Content-Security-Policy`;
- `X-Content-Type-Options: nosniff`;
- `Referrer-Policy`;
- `Permissions-Policy`;
- `Strict-Transport-Security`;
- запрет встраивания в чужие iframe.

**Готово, когда:** заголовки проверяются в ответах production-домена, а новый
deploy не требует очистки кеша браузера.

## P2 — поддерживаемость и тесты

### 19. `App.jsx` слишком большой

**Ошибка:** один файл содержит API-вызовы, данные, роли, экраны и модальные окна.

**Исправить:** разделить код на страницы, компоненты, auth provider, API-модули и
hooks. Удалить production mock-константы.

### 20. Автоматические тесты покрывают только часть backend

Сейчас в `tests/` есть 7 интеграционных тестов, которые запускаются в GitHub
Actions для веток `main` и `railway`. Они проверяют:

- login, refresh и профиль текущего пользователя;
- ответы `401`, `403`, `409` и `422`;
- создание пользователей, компетенции, задания и программы;
- назначение программы сотруднику;
- старт, сдачу, возврат и повторную сдачу задания;
- ограничение числа попыток;
- запрет сотруднику выполнять действия эксперта;
- запрет запуска задания вне назначенной программы.

Остаётся добавить проверки:

- блокировки пользователя;
- доступа к чужим материалам, заданиям и сдачам;
- загрузка и скачивание файла;
- миграции на чистой и заполненной БД;
- сохранение UI-состояния после обновления страницы;
- прямое открытие frontend URL.

## Порядок исправления

1. Исправить API helpers и единые статусы.
2. Подключить start, submit, review и block к backend.
3. Исправить создание submission и загрузку файлов.
4. Перевести программы, матрицы и задания с mock-данных на API.
5. Закрыть проверки доступа и добавить DB constraints.
6. Удалить `create_all()` и исправить bootstrap администратора.
7. Реализовать refresh/logout.
8. Исправить SPA fallback, healthcheck, кеширование и заголовки.
9. Добавить интеграционные и E2E-тесты.
10. После стабилизации декомпозировать frontend.

## Когда проект готов

Проект готов к production, если сотрудник, эксперт и администратор проходят свои
сценарии через реальные API, все изменения восстанавливаются из PostgreSQL/S3
после обновления страницы, а mock-данные не участвуют в работе интерфейса.
